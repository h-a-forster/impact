# Feature Request: Allow generation of Formatter for a type in a referenced assembly

## Is your feature request related to a problem? Please describe.

Given the following project structure:

 - Project A
    - `ProjectA.MyType`

 - Project B
    - References
        - Project A
    - Package References
        - MessagePack
    
I need to have a source-generated `IMessagePackFormatter` for type `ProjectA.MyType` generated **inside Project B** instead of Project A, because the latter has no (and cannot have) reference to MessagePack nuget package.

## Describe the solution you'd like

Add a `[GeneratedMessagePackFormatter]` attribute that will work for partial classes implementing `IMessagePackFormatter<T>`.

For example:

```csharp
[GeneratedMessagePackFormatter]
partial class MyObjectFormatter: IMessagePackFormatter<MyObject>;
```

That's it. The class does not even need to declare a body (no `{` and `}`), because the actual implementation is source-generated by `MessagePack.SourceGenerator.MessagePackGenerator` as usual.

As for the attribute-based property keys and other settings (such as Union), I can think of 3 alternatives:

1 - Use `System.Runtime.Serialization.DataMember` and related attributes. This is too limited IMO, as it cannot have `Union` and other features.

2 - Allow the generator and analyzers to work with user-defined versions of the MessagePack attributes. This would be similar to how you can declare dummy versions of BCL attributes that the C# compiler expects, such as [`[IsExternalInit]`](https://stackoverflow.com/a/67687186/643085) or `[ModuleInitializer]`. With this, I could simply copy and paste the attribute definitions for MessagePack attributes such as `[Key]` into my Project A, and have the source-generated formatter (as described above) pick them.

3 - Source-generate the attributes themselves using [`IncrementalGeneratorInitializationContext.RegisterPostInitializationOutput`](https://github.com/dotnet/roslyn/blob/main/docs/features/incremental-generators.md#outputting-values) instead of them existing in the `MessagePack.Annotations` assembly. This would allow using the attributes without adding an additional runtime dependency. Only compile-time reference to the analyzer Nuget would be required.

## Motivation

Project A is really a library (Nuget package), and I really want to keep it minimal. It currently has zero dependencies and I would really like to keep it that way.
